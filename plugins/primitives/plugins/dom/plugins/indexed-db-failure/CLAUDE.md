# indexed-db-failure

The one answer to "is this IndexedDB failure the browser's or mine?"
(`core/`, a page or a worker alike; no import, so a self-contained worker
bundle inlines it).

- `suspended`: WebKit cut the work short because it suspended this context.
  It never committed; redo it in a fresh context or skip it
  (`host-storage` boots again, the stall watchdog skips the record).
- `unavailable`: `UnknownError` (the spec's "unrelated to the database
  itself": WebKit's backing-store failures), `QuotaExceededError`,
  `SecurityError`.
- `fault`: everything else. Fail loudly.

`AbortError` and `InvalidStateError` are a fault here: only a caller knows
whether it aborted or closed something itself. One that never does may read
them as the browser's, in its own code (the watchdog's `stall-store.ts`).

Match by the spec's error name, never by a new message, unless the meaning is
narrower than the name (a suspension).

## Plugin reference

- Description: What an IndexedDB failure is about, from the error alone: idbFailureOf(err) answers suspended (WebKit cut this context's work short because its page or process was suspended — isSuspensionAbort), unavailable (the browser's own storage failed or refused: UnknownError, QuotaExceededError, SecurityError — Safari's "Error looking up record in object store by key range" among them) or fault (anything else: the caller's own bug, to fail loudly). Plain functions with no other import, so a self-contained worker bundle can inline it.
