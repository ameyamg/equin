# build-progress

The durable per-build progress log, `~/.equin/logs/build-progress/build-progress.jsonl`
(host-global, a bounded file sink: 2 MB × 2). `./equin build` opens one run per
invocation (`openBuildProgress`); op-runtime's span collector writes a
synchronous `enter` / `leave` line around every span, a 30 s heartbeat lists
the spans still open, and `finishBuildProgress` writes `done`. Every line is on
disk before the next statement, so a wedged or SIGKILLed build still names the
span it was in.

`readBuildProgress()` reconstructs each run. Its `lastAdvanceAt` is the last
time the run demonstrably MOVED — a span entering or leaving; the heartbeat
does not count, since it proves only that the process exists. That is the one
progress signal of a running build, read by:

- the build lock's wait policy (`build/cli/internal/build-holder.ts`), judging the
  holder of `.build.lock`;
- the install's stall rule (`installer/waits`), judging the holder of the build
  slot. An in-flight op record carries no steps (they land on its terminal),
  so the op log alone cannot tell a build that keeps moving from one that stopped.

## Why its own plugin

It used to sit in `op-runtime`. But op-runtime reaches `infra/jobs/supervised-job`,
which reaches `installer/waits`, so the install's stall rule could not read the log
without an import cycle. The log's only dependencies are the file sink, the
process footprint reader and the CLI's data dir. As a leaf, anyone judging a
running build can read it.
