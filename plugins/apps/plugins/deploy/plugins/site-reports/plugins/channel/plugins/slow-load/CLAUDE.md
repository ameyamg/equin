# slow-load

A site visitor's slow page load, as a report. The site's analytics already
measures every load (`analytics/collect`'s `load` on a hit), but a number in a
visit row reaches nobody; a report reaches the computer's Reports (through the
site's channel and intake, then the hourly mirror pull, `site-reports/import`).

**Site only.** It sits under `channel`, so `base-exclusions`
(`!apps.deploy.site-reports.channel.**`) keeps it out of every composition, and
the website names it. Main's own loads are slow-ops' `page-load`.

**One verdict per page load** (`web/components/slow-load-reporter.tsx`,
module-level state, so a remount never files twice), from the same milestones
analytics records — first byte, first contentful paint, ready (the later of
FCP and the route's content commit), ms from the navigation start:

- ready at or past `SLOW_PAGE_LOAD_BAR_MS` (3 s, about equin.ai's 85th
  percentile) → reported, its `phase` the largest stretch (`server`,
  `first-paint`, `app-ready`); judged once FCP is in, where paint is timed;
- hidden before ready after waiting the bar → `not-ready` (the visitor left or
  looked away; past 10 min it is clamped, not dropped);
- not visible at some instant before ready, and hidden before the bar → not
  waited (`background-load`); a prerendered page → not waited
  (`prerendered-load`). Counted as the intake's drops under that reason
  (channel's `countPageDrop`), never filed: its paint waited for the visitor.

**What the visitor could see is read from records that start with the page**
(boot-trace's `readPageShown`), never from the moment the reporter mounted:
the shell's inline first-hide record (`web-core`'s `index.html`, every
browser), Chromium's `visibility-state` entries (every one, not just the
first), and prerendering (`document.prerendering` / `activationStart`). The
first version checked only the first visibility entry at mount and subscribed
to `visibilitychange` then — so a tab switched away during the seconds before
the app booted was judged on a first paint that came minutes later, when the
visitor returned (equin.ai, 2026-11-20: "ready after 261.2 s", "183.4 s").

**Identity**: `<phase>:<mobile|desktop>` — at most eight rows on the site, each
counting every slow load of its kind; the latest sample is the row's payload
and path. **Payload**: the milestones, the bar, the coarse browser
(`coarseClient`: family and OS, never the user agent) and the network class
(`navigator.connection.effectiveType`, Chromium only), and where the first
byte went (`firstByte`: analytics' split — redirect/setup, DNS, TCP, TLS,
request → response, and the browser's own gaps between them, named by
position: before DNS, DNS→connect, connect→request — in the report's message) — nothing naming the
visitor. Lighthouse-style speed testers are bots at the intake
(`isBotUserAgent`), and automated browsers are dropped there too.

**Where a slow load's time went** (`split`, `core/internal/load-split.ts`;
read once, when the load is filed), up to ready or the hide. Read it in this
order. Which stretch: `codeRanMs` (the app's code had arrived), then
`contentMs` (the content committed; null with `waitingOn` = the boot step still
open), then the first paint — a paint long after `contentMs` with an idle main
thread is the browser drawing no frame. Then why:

- `documentEndMs` late → the HTML's own download;
- `lastFileEndMs` late → the files: `bytes` over that time bounds the
  visitor's bandwidth from below (cached and untimed files count 0);
  `inFlight` still loading when they stopped waiting; one file far past the
  others in `slowest` is a stalled request
  (`queueMs` connection or queue, `waitMs` server or a lost response,
  `downloadMs` the transfer);
- `mainThread.busyMs` large → the device running the code (Chromium only,
  null elsewhere);
- `retries` → loads asked again after the page lost its reach;
- none of these → a boot step waited (`spans`), or a request still in flight
  (the browser times a request only once it ends).

Everything is cut at ready or the hide: a page hidden before it booted is
judged after, when the files the hide held up have ended, and their time away
is not the network's.

Files are named by path on the site's own origin only. The shell raises the
browser's 250-entry Resource Timing buffer (`RESOURCE_TIMING_BUFFER_SIZE`);
`filesTruncated` says it still filled. A page whose app never boots files
nothing: this reporter is part of the app.

Verify: `e2e/slow-load-reported.ts` (a throttled visitor load reports, an
automated one is counted as a drop), against a local website build or
`--url https://equin.ai`.
