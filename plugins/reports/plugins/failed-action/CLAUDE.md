# failed-action

## Why

A crash is filed as a report, and the reports engine rings ONE bell row per
report, bumping its count on a repeat; the bell's arrival toast is a 4 s
developer announcement shown once. Right for telemetry — but it also swallowed
the direct answer to the user's own click: on 2026-11-24 a sidebar row threw
`MissingRouteParamError` in its click handler, and the user clicked it 11 times
seeing nothing (report-1795534089-iyie4i). This plugin is that answer, given in
the tab, at once, with no server round-trip and on every occurrence. The
report, its dedup and its bell row are untouched.

## What counts as the user's action failing

An `error` event raised while a trusted user-action event (click, key, submit,
input, paste, drop… — `USER_ACTION_EVENTS`) is still being dispatched, i.e.
thrown synchronously by a handler of that input (`web/internal/input-dispatch.ts`):

- The browser reports a listener's throw inside the dispatch, and React 19
  routes its handlers' throws through `reportError`, which dispatches `error`
  synchronously — so the input is still in dispatch when the listener runs.
- "Still in dispatch" is `eventPhase !== NONE`: a boundary, not a time
  window. It holds the listeners and the microtask checkpoint after each
  (so a React sync render the click caused counts); anything in a later task —
  a timer, a live push, a fetch continuation, a deferred render — never does.
  The one stretch it can over-claim: a background React update's effects that
  the click's own render flushes first, and only if one throws past every
  error boundary.
- `isTrusted`: the user did it. A script's dispatch nested inside a trusted
  one still counts (it is inside it).
- A stack frame provably foreign (a browser extension's listener —
  `crash`'s `pageCodeOrigin`) is not the page's action failing.

Not claimed: a throw in a window capture listener registered before this
watch, input inside an iframe, and an async handler's failure after an `await` (an unhandled
rejection, later, with nothing tying it to the input). A write that fails has
its own toast (`reports/mutation-errors`, the optimistic layer's rejections).

## What the user sees

Everyone (not only developers): an error toast "That didn't work — Something
went wrong. It has been reported.", staying until dismissed; a developer also
sees the error's name and message as its detail. A repeat replaces the toast on
screen (`useToast`'s `replaces`) instead of stacking, so every click visibly
answers without piling up. It is also a bell row (`useToast` records every
toast), de-duplicated per message. Like every error a tab raises, that row's
first write is announced for 4 s in the user's other open tabs (its meta line
says "another tab"). A developer also still gets the reports engine's own 4 s
"Crash recorded" announcement on a report's first occurrence.
