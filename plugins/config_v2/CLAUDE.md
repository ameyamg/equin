# config_v2

See [config v2 vision](../../research/2026-05-16-config-v2-vision.md) for the
full design rationale, planned field types, and storage model.

## Declaring config (plugin author)

```ts
import { defineConfig } from "@plugins/config_v2/core";
import { boolField } from "@plugins/fields/plugins/bool/plugins/config/core";
import { textField } from "@plugins/fields/plugins/text/plugins/config/core";
import { listField } from "@plugins/fields/plugins/list/plugins/config/core";

export const myConfig = defineConfig("my-plugin", {
  fields: {
    enabled: boolField({ label: "Enabled", default: true }),
    name: textField({ label: "Display name" }),
    items: listField({
      label: "Items",
      itemFields: {
        title: textField({ label: "Title" }),
      },
    }),
  },
});
```

Each field carries its Zod schema, default value, and UI metadata; the settings pane
renders them automatically. Field types live under `plugins/fields/plugins/`; see
[fields/CLAUDE.md](plugins/fields/CLAUDE.md) to add new ones.

## Reading config

**Web:** `useConfig(myConfig)` returns reactive values that update live. It answers the
(normally unreachable) window where the document is not known yet with
`descriptor.defaults` — fine for a cosmetic read, WRONG whenever the value decides what the
surface asserts (which views/items exist, whether a mode is on): defaults are a legitimate
answer, so a consumer cannot tell "the user configured nothing" from "we don't know yet".
Those reads use **`useConfigResult(myConfig)`**, which returns live-state's
`ResourceResult` (`status: "loading" | "error" | "ready"`) and makes the unknown window a
state to render (`live-state/no-pending-data-collapse` lints the collapse). Both live values it
reads (`configValues`, `configScopes`) are `preload: "boot-and-keep"`: every document a first
paint can read rides the boot snapshot and is never evicted, so `loading` after a successful
boot is unreachable rather than merely rare.

**Git-defaults preview (web, per tab).** `setConfigPreview(true)` makes every
`useConfig` / `useConfigResult` read in this tab resolve to the committed layer —
`configGitValues` (`config-v2.git-values`, `{ path, scopeId? }`), served from
`ConfigGitLayer.document` and watched through `ConfigGitLayer.watch` — i.e. what a
brand-new user sees, with no user override or runtime fork. Every `useSetConfig` write
is refused while it is on — announced through `onConfigWriteRefused("preview", …)` (the preview plugin's action-bar mark toasts it; config_v2 cannot import the toast, whose chrome reads config). Kept in session storage (survives a reload, dies
with the tab); `useConfigPreview()` reads it. Server-side `getConfig` reads are not
affected. The switch is `config_v2/plugins/git-defaults-preview` (View options — "Preview default config",
developers only — and always while on, since the committed Developer mode is off).

**Server:** `getConfig(myConfig)` reads the current value from the in-memory
cache. `watchConfig(myConfig, cb)` notifies on changes.

## Descriptor provenance (`source`)

Every `ConfigDescriptor` carries a `source: "manual" | "reorder" | "view"`, set by
`defineConfig` (defaults to `"manual"`), distinguishing **hand-authored** configs from
the two **auto-generated** families — one descriptor per reorderable render slot
(`reorderDirectiveDescriptor`) and one per DataView consumer (`viewsDescriptor`). Named
`source`, **not `origin`**: `origin` already means the `.origin.jsonc` layer here.

`source` lives on the descriptor object only — **not** in the config document or schema,
so it never affects an origin `@hash` or `config-origins-in-sync`; the settings config nav
surfaces it as a filterable `enum`. A new primitive that generates descriptors must give
itself its own `source` value.

## Three-layer config model

Config flows through three layers, each with a human-editable override mechanism:

```
Code (defineConfig)  →  git config/  →  ~/.equin/state/config/
   defaults + schema      repo defaults     user config
```

### Layer 1: Code → git (build-time)

`./equin build` generates `config/<plugin-tree>/<name>.origin.jsonc` from `defineConfig` defaults. First line: `// @hash <12-hex>` (content hash).

**Agent overrides:** Copy to `config/<plugin-tree>/<name>.jsonc`, edit values, keep the `// @hash` line from origin.

**Conflict detection:** when origin regenerates with a new hash, `config-origins-in-sync` fails on any `.jsonc` override still referencing the old one. Review the origin change, update the override, restamp `// @hash`.

### Layer 2: git → user (the backend that reads it, at boot)

The user layer is per **config generation**: `~/.equin/state/config/<namespace>/gens/<id>/`, where `<id>` is `CONFIG_GENERATION` (`core/config-generation.generated.ts` — a hash of the committed `config/` tree, the plugin-move ledger, every config migration and the merge engine, regenerated by every build and held by `config-origins-in-sync`). The namespace's `HEAD` names the generation it serves. The build writes no user config: the **serving backend whose code reads a generation derives it** — see [Config generations](#config-generations-the-backend-that-reads-config-derives-it). Propagation writes the resolved git config (override if present, else origin) to `<gen>/<plugin-tree>/<name>.origin.jsonc` with a hash of the source content.

**User overrides:** UI `setConfig` or manual edits create `<gen>/<plugin-tree>/<name>.jsonc` with the origin's content hash. A manual edit may leave the `// @hash` line out: the registry stamps it with the origin's hash (see [Conflict precedence](#conflict-precedence-origin-wins-until-reconciled)).

**Conflict detection:** When git config changes, the propagated origin hash updates, and a user override still carrying the old hash becomes a **conflict**: the new git value takes effect, and the settings UI surfaces the conflict (Keep / Accept / Merge) — see [Conflict precedence](#conflict-precedence-origin-wins-until-reconciled). A user override therefore never silently masks a committed change; it only wins while the git value it was written against is unchanged.

### App scopes: per-app config in git

A descriptor's config can be customized **per app** straight from version control — no code declares scopes; you commit a JSONC file at an `@app/<id>` path and `./equin build` does the rest. The app whose id is `<id>` then resolves the scoped values; every other app keeps the base value.

**To customize app `<id>` for the descriptor at `<plugin-tree>` (config name `<name>`, usually `config`):**

1. Create `config/<plugin-tree>/@app/<id>/<name>.jsonc`.
2. Put **only the fields that differ** for that app, e.g. `{ "captureUrlByDefault": false }` (a partial delta — schema default-backfill fills the rest).
3. Line 1: `// @hash <hash>` copied from the **base** origin `config/<plugin-tree>/<name>.origin.jsonc`. A scoped override anchors to the base origin — **no scoped origin is ever committed**.
4. `./equin build`. Propagation resolves the scope as `baseEffective ⊕ scopedDelta` and writes it to `~/.equin/state/config/<wt>/<plugin-tree>/@app/<id>/<name>.origin.jsonc`.
5. `./equin check config-origins-in-sync` validates the `@hash` against the base origin and the document against the schema.

This is the base-override workflow (Layer 1) one path segment deeper. Any registered descriptor can be git-scoped — it does **not** need `scope: "app"` (that marker only governs the theme "Customize for app" fork-all-descriptors UX).

**Reading a scoped value (consumer):** thread the app scope yourself — `config_v2` is app-agnostic. `useConfig(cfg, { scopeId: appId ? \`app:${appId}\` : undefined })` with `appId = useCurrentAppId()`. Every scope with its own config is preloaded by the boot snapshot (with the scopes map that decides it), so the scoped value paints on the first frame (no flash). On the server, `getConfig(cfg, "app:<id>")`.

**Scoped read/write are symmetric.** Both ends key off the **same** server predicate, `scopeHasOwnConfig(descriptor, scopeId)` (the scope's origin OR override exists), so they can never disagree:

- **Read.** `useConfig` decides whether to read the scoped document purely from membership in the live `configScopes` map (`config-v2.scopes`, param-less: every server-registered storePath → its scope ids), recomputed from `scopeHasOwnConfig` on every scoped-file change — so a scope counts whether it became real via a committed git scope, a theme fork, **or a plain scoped `setConfig` write**. A non-member scope's read is skipped (`useLive(configValues, null)`) and the global document is used; a member's document not settled yet falls back to the global value, never `descriptor.defaults`. While the map itself is unknown a scoped read is `pending` (preloaded, so only after a failed boot). The same map lists every registered path, which is how `useConfigResult` throws on a web-only half-registration. `useScopeMembership` returns the membership as a `ResourceResult<boolean>` (the theme "Customize for app" toggle reads it) but does **not** gate `useConfig`.
- **Write (fork-on-write).** A scoped `useSetConfig`/`setConfig` to a scope with **no own config yet** auto-snapshots the current base into that scope's origin (the same redacted snapshot `forkScope` writes) and then writes the override — no explicit fork ceremony. A write when no **base** origin exists at all still throws "run ./equin build".

**Semantics:** a committed scope is a frozen snapshot of `baseEffective ⊕ delta` recomputed each build, so its non-overridden fields track the git base as of the last build, not a runtime base edit. A runtime user fork layers on top; un-customizing drops the runtime override and falls back to the committed scope, not to global. The fork wins only while its hash matches: committing (or changing) the scope rewrites the scope's origin under a runtime fork, so the fork goes stale — the committed value takes effect and the user sees a conflict, exactly as for a base override.

**Per-app scopes in settings:** the config detail pane is scope-aware — a **Base** tab plus one tab per customized app (live from `configScopes`); selecting a tab re-keys every read and write to that `scopeId`. **`+` App** forks a new per-descriptor customization (`fork-descriptor-scope`); **Stop customizing** (`remove-descriptor-scope`) drops the descriptor's whole per-app customization — distinct from "Reset all", which only reverts edits to the scoped origin.

### Config generations: the backend that reads config derives it

A deploy used to rewrite the user layer (plugin moves, migrations, propagation) **before** the new backend served, so the backend still serving read new-shape files (a migrated shape failed its old schema → invalid banner, defaults), and a failed deploy reverted the web bundle but never the config. Now each config-relevant code version has its own generation, and only the process running that code writes it (`machine/internal/generation.ts`, layout in `core/internal/generation-layout.ts`):

```
<ns>/HEAD                { generation, history } — the generation served
<ns>/.generation.lock    flock: derive → promote, and a write to HEAD's generation
<ns>/gens/<id>/…         one whole user layer (origins, overrides, ancestors, merge records, applied-ledger markers)
<ns>/gens/<id>/.retired  once HEAD moved past it
```

- **Derive** (the store's `open`, first thing in `initRegistry`, serve mode): when `CONFIG_GENERATION` is not HEAD's, the backend takes the lock, reads HEAD's generation (or the pre-generation flat `<ns>/` layout) into memory, replays the move ledger and every migration (live descriptors), propagates its committed layer (`propagateUserLayer`) — the engine is `machine/internal/user-layer/`, the move ledger comes from the generation module (`CONFIG_PLUGIN_MOVES`), loaded with a literal `import()` (generated after the build imports the barrels, so no barrel may reach it statically; restart-skip still follows it) — writes the result to a temp dir and renames it into `gens/<id>/`. All in memory between one async read and one async write — no blocking fs on the backend. The boot auto-merge sweep then runs on it. Most deploys don't change config: old and new backend share one generation, as before.
- **Promote** (machine `onReady`, after `markServerReady` — when the gateway swaps the backend in): HEAD names it, the replaced generation gets `.retired`, every generation but those two is collected, the lock is released.
- **The lock spans derive → promote.** A write to HEAD's generation holds the lock around itself (`withWrite`, in the file store's `edit`), so the backend still serving either writes before the clone (carried over) or waits and is then refused with `ConfigGenerationRetired` — never lost between the two. A generation not HEAD's yet (a booting backend's `exec` children) writes freely: it cannot be retired under them.
- **Failed deploy**: HEAD never moves and nothing the serving backend reads was touched; the half-derived generation is derived again by the next attempt (the process dying released the lock).
- **Code coming back** (its generation was HEAD before — a reverted config change, a rollback): when HEAD's generation applied nothing it does not know (its markers' move and migration keys are all this code's), it is derived again from HEAD like a new one, so writes since carry over. Otherwise (HEAD applied a migration or move this code does not know — one-way) it reuses its old generation as it was and says so on the `config-generations` log channel (writes since are not carried); collected, its boot fails (`ConfigGenerationMissing`). An `exec` child requires its generation on disk.
- **Readers off disk** (`readEffectiveConfigFromDisk` callers, e2e scripts, the relocate CLI) read `servedConfigDir(ns)` (`config_v2/plugins/disk-read`): HEAD's generation, or the flat layout before any. A worktree is forked from main's served generation, copied flat; a composition reset removes `<ns>/` and its cold start derives from scratch; a release backend derives from its bundle's `config/` like any other.
- **From the flat layout**: the first generation-aware boot derives from `<ns>/` itself and leaves it as is. A pre-generation backend writes it without the lock; a file it changed during the derive is named in an error at promote (it stays at `<ns>/`).

### Hash chain

Each layer's override records the hash of its *own* origin on line 1: a git override's `// @hash` tracks code changes; a user override's tracks git-config changes (code *and* agent overrides).

### Override semantics

Overwrites are **full copies**, not deltas: `setConfig` writes `{ ...currentValues, [key]: newValue }`, always a complete document. `parseDocument` fills missing keys from defaults, so a hand-written partial file still degrades gracefully.

### Conflict precedence: origin wins until reconciled

`effective(origin, overwrites)` normally returns the override when it exists. But when the override's `// @hash` is stale (a **conflict** — the origin moved underneath an override written against an older version), the **origin takes precedence** until the user reconciles: edit a field (rewrites the override against the current origin), "Keep my values" / acknowledge-conflict (bumps the hash so the override wins again), "Accept new defaults" / delete-override (drops the override), or **"Merge"** / merge-conflict (below).

### Three-way merge (ancestor snapshot)

"Keep my values" and "Accept new defaults" are all-or-nothing. The **Merge** resolver carries the user's override onto the new origin: what only the user changed is kept, what only the update changed is taken, and whatever it cannot decide stays a conflict.

A three-way merge needs the **base** — the origin the override was written against — but only its hash lives in `// @hash`, and the user-layer origin is propagated by build, not versioned. So `propagate()` **snapshots the base at the conflict transition**: about to overwrite a user origin an *in-sync* override depends on (`oldOrigin.hash === override.hash && override.hash !== newHash`), it first writes the old origin to a sibling `<name>.ancestor.jsonc`. That predicate is idempotent — once the override is stale the hashes differ, so repeated propagations never clobber the true base — and `propagateUserLayer` (`machine/internal/user-layer/`) deletes any orphaned ancestor of a document out of conflict.

The capture covers `@app/<id>` scopes too (`propagateGitLayerDocument` hands each scope its own ancestor), and the propagation deletes a document's ancestor once it is out of conflict.

**`mergeConfigDocument({ descriptor, base, yours, theirs })`** (pure, `core/internal/merge/`) is THE merge — the Merge button (`mergeConflictByPath`), the banner's `trueConflictKeys` (`computeDescriptorConflict`, via `mergeConflictFields`) and the boot auto-merge all run it, so they cannot disagree. It returns `{ status: "merged" | "conflict", document, decisions, reasons?, issues? }`:

- **Completion first.** `yours` is `base ⊕ override` — a partial override (`{ "enabled": true }`) changed one key, it did not delete the others — and all three sides drop the `auto-` row ids `normalizeCollectionItems` seeds, so they don't read as a row deleted plus one added.
- **Deep** (`deepMerge`, `deep-merge.ts`). Objects merge per key. Lists merge per row when every row has a unique key (`id` > `item` > `label` > the string itself); otherwise both sides changing one is a conflict (`unkeyed-list`). A row only one side added goes after its neighbour from that side. In a reorder tree's `items` the user's order wins; elsewhere both sides reordering differently is a conflict (`order`). The update removing something the user changed is a conflict (`delete-modify`).
- **Both sides changed the same value**: the user's wins, listed as a `yours-won` decision. A key the user changed that neither the descriptor nor the new origin has is dropped and listed (`removed-dropped`).
- **Retired fields** (`descriptor.retiredFields`, below): a value the user changed under a renamed key is carried to the new key (`removed-renamed`, unless the user also set the new key); under a removed key it is dropped with the declared reason (`removed-dropped`, `reason`).
- **Schema gate.** The merged document must pass `descriptor.schema`, else it is a conflict with `issues`.

`mergeConflictByPath` writes the merged document under the new hash and deletes the ancestor on `merged`; on `conflict` it writes nothing and returns the undecided top-level fields. Every terminal resolution (acknowledge-conflict, delete-override) also deletes the ancestor. `merge/corpus.test.ts` replays committed overrides restamped in `config/**` history (`merge-corpus.json`) and asserts none is left undecided, none gains a duplicate row or brings back a row either side deleted, and how many match the committed resolution. Design: [`research/2026-11-24-global-config-auto-merge.md`](../../research/2026-11-24-global-config-auto-merge.md).

### Automatic merge (`<name>.merge.jsonc`)

A user should never have to click Merge for an update that merges cleanly. At boot, `initRegistry` runs `autoMergeDocumentNow` on every document (base and each app scope) BEFORE reading it: a stale override with an ancestor whose `mergeConfigDocument` result is `merged` (the descriptor's live schema passing) is applied in one `auto-merge` store edit — the record first, then the merged override under the new origin's hash, then the ancestor removed. Anything it cannot decide stays the normal conflict. User layer only; committed `config/**` merges stay manual. A new generation is derived before this sweep, by the backend running it, so the sweep merges against the schema of the code that reads the result.

The record (`ConfigMergeRecord`, `core/internal/merge/merge-record.ts`; file kind `"merge"`, header = `toHash`) holds the inputs, the result, the decisions and the exact pre-merge override and ancestor. It is NOT part of `documentStamp`, so writing it alone moves no value, conflict or tier. `mergeRecordStatus` says where it stands: `undone`, `current`, `superseded` (the origin moved past `toHash`) or `edited` (the override no longer holds `result`). A plugin move's ledger rewrite re-stamps a record with its origin (header and `toHash`); a config migration supersedes it.

- `undoAutoMergeByPath` writes the pre-merge files back (a normal conflict again) and stamps the record `undoneAt` — a tombstone, because the restored conflict is exactly the boot sweep's input: the sweep skips a document whose tombstone names the current origin (`toHash`), and a later update merges again over it. Refused (`AutoMergeUndoRefused`) unless `current`.
- `stampAutoMergeByPath(path, recordId, "acknowledgedAt" | "notifiedAt")` stamps only the record it names, then runs the document fan-out (values unmoved) so record readers move.
- Delete-override, a per-field reset that removes the override and Stop customizing remove the record with the ancestor. The agent-write ledger, the memory store, the orphan audit (`merge-record` role, noise) and `configFileOwner` all cover the file.

The live values, endpoints, banner and update notification are [`plugins/auto-merge`](plugins/auto-merge/CLAUDE.md).

**Every config file carries a `// @hash` header** — the anchor conflict detection compares against. Origins, ancestors and committed files are written only by the build and the registry, so one without it is corrupt: `parseConfigFile` throws (the file store's `read` of an origin / ancestor, the git layer), and `setConfig` throws rather than write an override when no origin has been propagated.

**A user override is the one file written by hand, so its hash is derived, never asked of the writer.** An override with no header (`parseOverrideFile` → `hash: null`, "unstamped") was written against the origin beside it; the registry stamps it with that origin's hash the first time it reads it (`readEntryValues`, in the document's lock — a `stamp-unstamped-override` edit), and propagation (a generation derive) stamps it with the origin it is about to replace. So a hand-written override is applied as soon as it lands and then joins the conflict chain like one `setConfig` wrote. (It used to be refused: the reader threw from the watcher's re-read, the crash went to the worktree's reports, and the app kept serving the old value with nothing on screen saying so.)

Because the running app resolves to origin during a conflict, the settings editor binds to `conflictEntry.overrideValues` (the user's override document on disk), not to `useConfig` (the resolved value) — otherwise the user could neither see nor fix their pending override.

**A document in conflict refuses every write computed from what the app shows.** The app shows the new origin, so a surface writing back what it shows would replace the user's parked value of that key with the new default — and a whole list is one key (a DataView's `views`: toggling one option rewrote every saved view as the defaults). `setConfig` throws for a document in conflict unless the write is `fromOverride: true` (the `set-field` body's flag), which only the settings editor sends, since it binds to the override. `useSetConfig` reads `config-v2.conflicts` and refuses before sending, announcing `{ kind: "conflict", storePath, scopeId? }` through `onConfigWriteRefused` — `config-link`'s `ConflictWriteToast` (at `Core.Root`) says "Config has a conflict — resolve it first" with a **Resolve** link to the config.

### Config migrations (saved values after a shape change)

When the shape a field STORES changes (a value re-spelled, a key renamed), the
user layer — not in git — must be rewritten once per namespace. Declare it on
the descriptor:

```ts
defineConfig({
  migrations: [defineConfigMigration({ id: "saved-icons-to-symbols", apply: (doc) => … })],
  fields: { … },
});
```

The backend deriving a new config generation (before it propagates) applies
every migration the generation it starts from has not applied yet — with its
LIVE descriptors — to that config's origin, override and ancestor documents,
base and `@app/<id>` scopes, and records it in `.config-migrations-applied.json`
(inside the generation); a namespace with no saved config records them without
running. Hash chains are kept (a rewritten origin gets its new
hash and its override is re-stamped), so overrides stay in force. `apply` must
be idempotent; never delete a migration that may not have run everywhere. The
committed `config/` files are rewritten by hand in the same diff. The ledger
engine (`runConfigLedger`, `rewriteConfigFiles`, over an in-memory `ConfigTree`) is
`machine/internal/user-layer/`,
shared with plugin moves.

### Removed and renamed fields (`retiredFields`)

A config's schema is `.passthrough()`, so a saved value under a field key the
code no longer declares is never flagged: the new key backfills its default and
the setting silently reverts. So a field key that goes away is **declared**,
one of two ways:

```ts
defineConfig({
  fields: { instructions: textField({ … }) },
  retiredFields: {
    prompt: { renamedTo: "instructions", reason: "renamed to instructions" },
    legacyMode: { reason: "the legacy runner is gone" },
  },
});
// or, when saved documents must be rewritten:
defineConfigMigration({ id: "prompt-to-instructions", renames: { prompt: "instructions" }, removes: ["legacyMode"], apply });
```

Keys are dotted paths, through `objectField` sub-fields (`limits.max`); a
list's rows are data, not walked. `defineConfig` refuses a retired key that is
still a field and a `renamedTo` that is not one. The automatic merge reads
`retiredFields` (above); a migration has rewritten the documents before any
merge reads them.

`config-v2:fields-retired-declared` (`check/fields-retired-declared.ts`, rule in
`check/fields-retired.ts`) enforces it: every field key path a registered
descriptor's committed origin held at `git merge-base HEAD main` (read with
`git cat-file --batch`, so an origin not regenerated yet still counts) that the
current descriptor neither declares as a field nor as retired (`retiredFields`,
a migration's `renames` keys / `removes`) fails. A config with no origin at the
merge base (new, or its plugin moved — the move ledger's business) is not
judged. The merge base is part of its cache signature, as in
`published-migrations-immutable`.

### Plugin moves and stranded overrides

A config's user-layer path is its plugin's id, so moving a plugin moves where its saved settings must live. `./equin plugin move` records every move in a committed ledger, and the backend deriving a config generation replays it (the ledger as its code was built with it — codegen bakes it into the generation module as `CONFIG_PLUGIN_MOVES`, each entry with its key and whether its old id is a plugin again) before propagation — folder moved, saved reorder keys re-rooted, `// @hash` chain kept so overrides stay in force. See `plugins/plugin-meta/plugins/relocate/CLAUDE.md` ("Saved settings follow the move").

An override that still ends up where no live config reads it (plugin removed, or a move onto a destination that already had settings) is found by the orphan audit (`debug/config-orphans`' machine half, over the desktop's config dir) — never deleted, since the user layer is not versioned. `debug/config-orphans` shows it: a notice pinned above Settings → Config, the Debug → Config Orphans panel, and one rolling `config-orphans-stranded` report filed at boot.

### Schema evolution

Adding a field to an existing config (including a `listField` item or `objectField` sub-field) must not break documents stored before the field existed. Two mechanisms guarantee this:

- **Default-backfill.** Every `FieldsRecord`→`z.object` composition (`fieldsToZodObject`, `listField`, `objectField`) wraps each field schema via `fieldSchemaWithDefault(field)` = `field.schema.default(field.defaultValue)`, and `defineConfig` builds its schema as `fieldsToZodObject(fields).passthrough()` (`fieldsToZodObject` is strict; config adds the unknown-key tolerance). A key missing from a stored document heals to that field's default instead of failing validation; the file self-heals on the next `setConfig`.
- **Invalid surfacing, not silent fallback.** When the effective document still fails the schema after backfill (a genuine break — a field's type changed under stored data, a bad hand edit), `readTypedConfig` resolves to defaults *and logs a warning*, while `computeAllConflicts` emits a `kind: "invalid"` entry carrying structured `issues` (`{ path, message }`, see `configV2ValidationIssueSchema`) that the settings detail renders as a destructive banner pinpointing each bad field — so disappearing data is never silent. Hash conflicts (`kind: "hash"`) take precedence when both apply. A missing document is the legitimate defaults case, not an "invalid" one.

### Checks

`config-origins-in-sync` (single check, double duty):
1. Every `.origin.jsonc` in `config/` matches current `defineConfig` defaults
2. Every `.jsonc` override has a `// @hash` matching its current origin

`config:overrides-authored` (`check/overrides-authored.ts`) — see
[mandatory overrides](#mandatory-overrides-requiresauthoredoverride) below: a filesystem
scan of `config/**/*.jsonc` (excluding the generated `.origin`/`.ancestor` siblings)
failing on any file still carrying the seeded `// @review` marker. `alwaysRun` (fails
`--skip-checks` builds too) and never cached — the marker is minted by the build itself,
after that run's tree hash was taken.

`config-v2:registrations-paired` (`check/registrations-paired.ts`) — every server
`ConfigV2.Register` (in the plugin's `server/` or `machine/` barrel — register from a
portable `server/` whenever the plugin's web half can render in a browser host, see
below) has a matching web `ConfigV2.WebRegister` at the same
storePath, and vice versa.

The same check runs the **config arm of the browser-host coverage guard**
(`resolveHostConfigCoverage`, codegen's `core/browser-host-coverage.ts`): every
`ConfigV2.WebRegister` contributed by a web plugin a browser host scopes its page to
(`webPlugins` of the host's inferred graph) — for a descriptor whose owner is scoped too —
has a `ConfigV2.Register` at the same storePath in a `server/` barrel of the host's worker
graph (never `machine/`, which no browser host boots). Keyed by the REGISTERING plugin
(reorder plants directives under other plugins' ids). It runs here rather than in the
graph derivation because it reads the barrels' contributions, which the barrel-free
registry phase cannot import. **Nothing exempts it, and config has no `needsMachine`
escape**: a registrar the worker cannot boot is made portable, split (its
`ConfigV2.Register` moved into a portable `server/` half, the engine into `machine/` or an
engine child — `build`, `reports`), or left out of the host's composition. Each gap names
the storePath, the scoped web barrel registering it, and why every server-side registrar
is outside the graph (desktop-only `machine/`, not in the composition, or the non-portable
barrels and computer-bound modules that keep it out). Both halves read registrations
through one pure `collectConfigRegistrations` (`check/config-registrations.ts`).

### Mandatory overrides (`requiresAuthoredOverride`)

A descriptor whose committed override must be **deliberate, not defaulted** declares
it:

```ts
defineConfig({
  name: slotId,
  requiresAuthoredOverride: {
    guidance: ["Arrange \"items\" for how this slot renders", "(sidebar = vertical list, toolbar = horizontal bar)"],
    // Optional. "Is there anything here to author?" — omit to always seed.
    seedWhen: { field: "items", minLength: 2 },
  },
  …
})
```

`./equin build` then does the mechanical half: it **seeds** a missing
`config/<tree>/<name>.jsonc` from its origin — same `// @hash`, same body, same legend
comments — with a one-line `// @review` marker plus the descriptor's `guidance` lines
after the hash header; and it **re-marks + re-stamps** an existing override whose origin
hash moved underneath it. The human half is: arrange the values, delete the marker line.

`seedWhen` gates **creating** a file, and only that. It is data (`SeedCondition`: the
origin's `field` holds an array of at least `minLength` entries, read by
`seedConditionHolds`), never a function: the build reads descriptors from the evaluated
barrel records, which hold no code — a predicate made every build import every barrel
live just to ask it. Some defaults are vacuous —
a render slot with no contributions has no arrangement to make, so `{"items": []}` would
be a review a human can only rubber-stamp, burying the files where a decision is pending.
`defaults` is the ORIGIN's effective document (post `OriginDefaultsProvider`), not
`descriptor.defaults` — reorder's catalog is materialized at build time, so its field
default is always `[]`. The descriptor stays REGISTERED regardless: never express this by
withholding the descriptor, or `pruneOrphanedConfigFiles` deletes an authored override the
moment its slot empties. An existing file is never seeded, deleted or skipped — and still
re-marks when it goes stale, since "your slot lost every contribution" is worth saying.

`guidance` is **descriptor-supplied prose**, so neither the engine nor the check ever
names a config family — the check just echoes each offending file's own marker block back,
and a new family that opts in needs zero edits to either. Today's consumers: reorder's
`reorderDirectiveDescriptor` (per reorderable slot) and data-view's `viewsDescriptor`
(per DataView surface).

Why *review* rather than *presence*: seeding makes absence self-healing (delete a
required override and the next build re-seeds it, marked, which fails), and a stale hash
stops being discharged by retyping it — retyping was acknowledgement, not review.

Seeding is **build-only** (never in the shared `regenerateManifestCodegen` pipeline)
because `regen-generated` runs inside push's merge-driver path followed by an amend
commit, so a marker minted there would land unreviewed; it asserts marker-free instead.
Design:
[`research/2026-07-23-global-authored-override-seeding.md`](../../research/2026-07-23-global-authored-override-seeding.md).

### Override legend (`overrideLegend`)

`defineConfig({ overrideLegend: [...] })` declares how to hand-write the descriptor's
values. The build keeps those lines as a `// @legend` block right under `// @hash` in
**every** existing committed override (base and `@app/<id>/` forks) — `withOverrideLegend`
(core) is the one writer, called by the `overrideLegends` step of the shared codegen
pipeline and by the seeder. Re-stamped every build because nothing else keeps it: the
runtime writer re-serializes without comments, and authors delete what they don't need
today. The block is build-owned (hand edits inside it are lost); it never creates a file
or touches the body. Consumer: reorder's `reorderDirectiveDescriptor`
(`REORDER_NODE_LEGEND`), so every slot's layout file says a spacer exists.

### Internal architecture

**The server half is a registry over two host services; the machine half provides them.**
`config_v2/server` holds the registry, its live values and the scope routes, and reads no
file: every document goes through `ConfigStore` (`config-v2.store`, the user layer — `read`, `write`,
`remove`, `stamp`, `scopes`, `dropScope`, `watch`, `armed`, and `edit`, which every write path
runs its mutation through) and the committed layer, `ConfigGitLayer.document`
(`config-v2.git-layer`, one storePath's resolved committed document — the registry asks it
whether a scope is committed). Both are declared in `server/internal/host-services.ts` over the
`ConfigStoreImpl` / `ConfigGitLayerImpl` interfaces in `core/internal/store.ts`, which also holds
the one file layout (`configFileRelPath` and its inverse `parseConfigFileRelPath`);
`core/internal/memory-store.ts` holds `createMemoryConfigStore` (a browser host's user layer),
`core/internal/config-file.ts` the one `// @hash` reader (`CONFIG_HASH_RE`, `parseConfigFile`). `config_v2/machine` is the desktop: `fileConfigStore` (`machine/internal/file-store.ts` —
JSONC files under the namespace's config dir, the config-files watcher, the agent-write ledger),
`repoConfigLayer` (the checkout's `config/`), the watcher lifecycle (feeding
`notifyConfigDirChange`) and the raw-file view (`config-v2.raw-file`, `needsMachine`), which moves
with the document through the registry's `onDocumentChange`. The machine half imports through
`@plugins/config_v2/server`, never `../server/internal`, which is what gives its
`config_v2#machine` node its `dependsOn` edge on `config_v2`.

- **`mapConfigLists` (`core/internal/collections.ts`) — THE walk over every `listField` instance in a document**, at any depth (through `itemFields` and `subFields`). A config document is recursive; every consumer that walked it one level deep drifted. Used by `normalizeCollectionItems` (id seeding), the `config-stable-list-ids` check, and `diffNormalForm` (the layer-comparison normal form behind the tiers/modified attribution). It visits a list **before** recursing into its rows, because a row's `auto-` id hashes that row's content — seeding nested ids first would re-mint every enclosing id.
- **`readConfigFile` / `writeConfigFile`** (`machine/internal/jsonc-proxy.ts`) — async read/write with `// @hash` header tracking: the file store's `read` / `write`. The store is asynchronous end to end (a backend's thread never waits on the disk — `blocking-fs/no-sync-fs`); the tier cascade stays synchronous over files already read (`loadedProxy(await store.read(ref))`).
- **Per-document lock (`withDocument`, `registry.ts`).** Every read-then-write of one document — `setConfig`, reset, the conflict resolvers, fork/unfork, a watcher re-read, `reloadConfigDocument` — runs one at a time per `(storePath, scopeId)`, as the old synchronous store guaranteed by construction: two writers can't both base their write on the same override, and an older re-read can't land after a write's refresh. A locked section calls the unlocked helpers (`refreshEntryNow`, `ensureScopeEntryNow`) — never re-enter the lock.
- **`getConfig`'s scope membership comes from the cache entry** (`CacheEntry.ownConfig`, read in the same pass as its values), not the disk; the disk predicate (`scopeHasOwnConfigOnDisk`) feeds the scopes map, `getConfigScopeIds` and boot.
- **`ConfigWatcher`** (`machine/internal/config-watcher.ts`) — `@parcel/watcher` file-change detection on `~/.equin/state/config/`, behind the file store's `watch`. Debounce (100ms) + ceiling (1s); no reconcile timer (the file-watcher engine has none) — the blanket 30s reconcile it once had re-fired every watched path (2 per descriptor) into a full conflicts recompute, an O(N²) idle re-read storm with nothing changed. Callbacks are `() => void`; the registry re-reads through the store on notification.

  These events are a **push-latency** mechanism, not a correctness one — an event can be missed (an out-of-band writer parcel doesn't observe, a dropped fsevent, a path no `CacheEntry` registered). **Never treat "no event" as "no change"**: derived state must be founded on the disk, per the fingerprint memo below.

- **`refreshEntry` (`registry.ts`) — the single "this entry's files changed" path** (re-read from the store → replace `CacheEntry.values` → notify subscribers + `notifyDocument`). Called from **both** the watcher (out-of-band writes) **and every in-process writer right after its own write** (`setConfig`, `acknowledgeConflictByPath`, `mergeConflictByPath`, `deleteOverrideByPath`). The second is NOT redundant: on a missed watcher event a writer that waited for its own event would leave `entry.values` stale indefinitely, so `getConfig` — and with it the `config-v2.values` push and the boot snapshot's preload of it — would keep serving the pre-write document while the correct value sits on disk. Any new file-mutating path must call it (scoped fork/unfork instead rebuilds via `ensureScopeEntry`/`disposeScopeEntry`). It carries provider-backed (secret) field values forward — they live outside the JSONC document.

### Agent-write ledger (config an automated session overwrote)

Every config write takes a **required** `writer: WriteOrigin` (`ConfigWriteOpts`,
`registry.ts`) — `originOf(req)` at an HTTP boundary, `systemOrigin("…")` for a
job or boot. It replaced the trailing optional `scopeId`, so omitting it is a
`tsc` error rather than a silent downgrade. Named `writer`, not `origin`, for the
same reason descriptors carry `source`: `origin` already means `.origin.jsonc`.

When the writer is `agent`, the document's **whole trio** (origin / override /
ancestor) is snapshotted before the write, in config's ledger (`id: "config"`,
label "Config documents") of the shared
[`agent-write-ledger`](../infra/plugins/request-origin/plugins/agent-write-ledger/CLAUDE.md)
primitive — which owns capture, persistence, the divergence check and the
`/api/agent-writes` routes the e2e harness calls. The trio, not just the
override, because `forkDescriptorScope` writes the scoped origin too and the
conflict resolvers touch the ancestor.

config_v2 keeps two things, both in the desktop's file store
(`machine/internal/file-store.ts`). **The handle**, `configWriteLedger`, which
the store's `edit` records through — and every registry write path (and
`scope-fork.ts`) runs its mutation through `edit`. Its key is `<storePath>` or
`<storePath> @<scopeId>` (`machine/internal/config-ledger-key.ts`), read back out
by the restore. **The restore**, `applyRestore`: it puts the bytes back and then
has the registry re-sync through `reloadConfigDocument` (`refreshEntry` /
`ensureScopeEntry`). That re-sync is why the revert goes through the server
rather than the harness rewriting files: a filesystem restore would depend on the
`CONFIG_DIR` watcher, which is push-latency, not correctness (see above).

**Not covered:** provider-backed (secret) fields, which return before touching
the JSONC layer at all — an agent write there is not revertible by a bytes
ledger.
[`research/2026-08-30-global-agent-config-write-revert-ledger.md`](../../research/2026-08-30-global-agent-config-write-revert-ledger.md)

### Derived aggregates (conflict-locations / scopes / modified-counts)

Three aggregate live resources summarize all ~180 descriptors at once. They are cheap because none of them re-reads every config file per load — but they arrive at that in two *different* ways, and the difference is load-bearing.

All of config's live resources are live values (`network/live`), declared with `liveValue` in `core/internal/resource.ts` and served with `serveValue(…, { source: "external" })` in `server/internal/resource.ts` — external because their truth is the files on disk, which no change feed sees:

- `configValues` (`config-v2.values`, `{ path, scopeId? }` — `"scopeId?"` is an optional param; absent or `""` names the base document) and `configScopes` (`config-v2.scopes`, param-less) are `preload: "boot-and-keep"`. `configValuesServed`'s `preloadParams` names every registered `{ path }` plus every `{ path, scopeId }` in the SAME `scopeMembers` map `configScopes` is read from, so the scoped documents hydrated and the membership that selects them cannot disagree. Each tuple names the plugin its document is registered under, so a composition's boot snapshot carries only the documents of plugins its browser loads (the website does not carry the mail app's). This replaced config's own `Core.Boot` task, its `GET /api/config-v2/snapshot` endpoint and the `resident` flag (Resources page item 9).
- `configConflict` (`config-v2.conflicts`) and `configTiers` (`config-v2.tiers`), `{ path, scopeId? }`, move in lock-step with the document. Every writer calls ONE fan-out, `notifyDocument(storePath, scopeId)` (`registry.ts`): it derives the tuples a change moved once (a scoped change its own tuple; a base change the base tuple plus every known scope with no config of its own) and notifies all three per-document values for each, then refreshes modified-counts and conflict-locations. `config-v2.values` (and `watchConfig` subscribers) are skipped when the files moved but the resolved values did not (`refreshEntryNow` diffs them): a same-bytes rewrite or a reformat moves only conflicts, tiers and the raw file.
- `configConflictLocations` and `configModifiedCounts` (param-less) push through `configConflictLocationsServed.notify()` / `configModifiedCountsServed.notify()`. Neither is preloaded. While one is pending the attention dots render nothing, and the config nav renders its loading state until both have landed — its Modified / Conflict fields decide which rows a filtered view (the authored "Conflicts" view) keeps, so rows shown before then would claim "no conflicts".

**`config-v2.conflict-locations` — derived from disk, memoized on a file fingerprint.** Its loader is the authority: it re-derives, for every descriptor, WHICH scopes conflict (base and/or each on-disk app scope) through the *same* `derivedDescriptorConflict` memo the per-descriptor `config-v2.conflicts` resource uses, so the nav ⚠ badge, its tooltip, the scope-tab dots and the detail banner can't disagree. It reports scope ids rather than a boolean on purpose: a badge that only knows "somewhere" sends the user to a detail pane that opens on a clean Base and shows nothing. The memo keys `(storePath, scopeId)` on `(inode, mtime-ns, size)` of the file trio (origin / override / ancestor), so an unchanged descriptor costs 3 `stat`s, not 3 read+parse+hash. `inode` is what makes it airtight — `writeConfigFile` renames a temp file into place, so even a byte-length-identical hash restamp changes it.

The memo key comes from **the filesystem, not an event** — deliberately. `refreshConflictLocations` still runs from the watcher path, but only as a *push-latency* optimization (it diffs a "last published" snapshot and notifies on a flip); it is never the value the loader reads, so a missed watcher event can delay a push but can't produce a wrong answer.

**`config-v2.modified-counts` — derived from disk, through the same memo.** Its loader sweeps every registered descriptor and counts the BASE fields whose tier is `"user"` (below), so the nav badge and the detail pane can never disagree about what "modified" means. `refreshModifiedCount` survives only as the push path — it diffs a "last published" count and notifies on a flip — and is never the value the loader reads.

**Who reads config from a deployed site.** A visitor (network/live, *Who may
read*) reads `config-v2.values` and `config-v2.conflicts` of a document only
when a web plugin of the serving composition reads it — the plugin the
document is registered under is in `composedWebPlugins()`
(`visitorReadsDocument`, both values' `visitorTuple`): exactly the documents
the site's boot snapshot carries. Derived rather than declared per
descriptor: a page reading a document ships it to that page's visitor
anyway, and a hand-kept list would drift from what the pages read. Every
other per-document value (tiers, git-values, raw-file, the aggregates) is
owner-only; `config-v2.scopes` stays whole (every registered path and its app
scopes, no values — what every `useConfig` read keys off).

**`config-v2.scopes` (storePath→scopeIds) — still an event-fed in-memory map** in `resource.ts`, recomputed per changed descriptor by `refreshScopeMembers` (boot warm-up + `registry.ts`'s notify path). It reads nothing from disk per load — and so **does** go stale on a missed watcher event. Applying the fingerprint-memo treatment above is the intended fix; conflict-locations and modified-counts have had it, this one hasn't.

`config-v2.conflicts` is keyed per-descriptor (`{ path, scopeId? }`) so opening one config page recomputes one descriptor, not the whole ~180-descriptor map. `config-v2.tiers` is keyed the same way and rides the same memo record — as a **lazily computed slot**, because the conflict-locations sweep reads every descriptor's conflict entry and must not start paying to normalize and diff two documents it never looks at.

### What "modified" means

**A field is modified when the USER layer supplied its value — not when it differs from `descriptor.defaults`.** The git layer (the generated origin ⊕ any committed authored override, propagated down by build) is what the repo commits, and a value the repo commits is not something the user changed. The old basis marked all ~157 descriptors with a committed override as permanently modified, and every reorder slot always — a build-materialized descriptor's declared default is `[]` while its origin is the live contribution catalog.

`config-v2.tiers` is the single answer, per field, and everything reads it: the `git`/`user` badge, the accent stripe, the per-field Reset, the nav count badge, the "Modified only" filter, and the "Reset all" gate.

- **Which layer won is decided once**, by `readTypedConfigWithLayer` (`tier-logic.ts`) — the cascade `readTypedConfig` is now a wrapper over. Only a WINNING override can have modified anything: a stale, foreign or schema-invalid override is one the runtime resolves past, and it differs from the origin in every key. So **while a config is in conflict no field reads modified** — no stripes, no per-field Reset, no "Reset all"; the banner's Keep / Accept / Merge own that state, and "Reset all" was only "Accept new defaults" under another name.
- **`computeFieldTiers` (`server/internal/field-tiers.ts`) refines that to a per-key answer**, because `setConfig` writes FULL documents — a winning override "contains" the git layer's value for every field the user never touched. A key the override document omits is not an edit; it falls through to the git-vs-default comparison.
- **Both sides go through one normal form** (`diffNormalForm`, same file): drop `id` from rows of non-`stableIdentity` lists, at any depth, via `mapConfigLists`. `normalizeCollectionItems` seeds an `auto-<hash>` id on every id-less row on read and on write, so a user override carries them — while the BASE user origin is propagated byte-wise from a git origin codegen never normalizes and carries none. Without this, toggling one boolean marks every list field of that config modified forever. A `stableIdentity` list is left alone: its ids are durable external keys, so a differing id there is a real difference.
- **Per-field Reset restores the git-layer value**, not the code default (`resetConfigByPath`) — and when the reset leaves the user document saying nothing the origin doesn't already say, it DELETES the override instead of writing a copy of the origin into it, so a phantom override can't become a stale-hash conflict banner on the next build. Never while a conflict is open: deleting the override there is a terminal resolution that takes the ancestor (the merge base) with it.
- **`ConfigRegistration.descriptor` is typed `Omit<ConfigDescriptor, "defaults">`** so the settings pane cannot reach the code default at all. `defaults` stays on the descriptor itself (`useConfig` needs it for the pre-hydration window); withholding it from the registration is what stops a fourth surface from re-deriving "modified" the wrong way.

## Config in a demo scope (the browser host)

Inside a `<DemoScope>` config is the scenario's browser host's, like every
other key: the worker boots `config_v2/server` (portable) over two host
services, both portable providers in the host's graph:

- **Committed layer** — `config_v2/plugins/bundled-layer` (`ConfigGitLayer`):
  the repo's whole `config/` inlined as text (`import.meta.glob`, root-absolute),
  resolved per storePath by `committedDocument` (core) — `resolveGitLayer` over
  strictly parsed files (`parseConfigFile`; a hashless file throws). The same
  rule the desktop's `repoConfigLayer` (and the generation derive's
  `readCommittedLayer`) and the plugin-move ledger read the checkout with. `CommittedFiles` is a lookup
  over files already read, never a disk read: the repo layer reads the files one
  document needs without holding the backend's thread
  (`committedFilesFromMap`), and the tool processes read the whole dir once with
  `readCommittedFilesSync(dir, fs)` (core).
- **User layer** — `config_v2/plugins/browser-store` (`ConfigStore`):
  `createMemoryConfigStore({ propagatedFrom })` (core). The first time the
  registry touches a storePath, the store propagates its committed document
  into itself through `propagateGitLayerDocument` — the function a
  desktop backend's generation derive propagates with (`propagateUserLayer`) — so origins are a
  fresh user's (reorder's directives included: their committed arrangement,
  not `[]` defaults) and writes (`set-field`, served by `config_v2/settings`)
  land under the origin's hash. A reload is the committed state again; a
  persistent store (IndexedDB / OPFS) is the same interface.

`raw-file` needs the computer (`config_v2#machine`). Which config the page reads
inside the scope is what its scoped web plugins register; that each has a
