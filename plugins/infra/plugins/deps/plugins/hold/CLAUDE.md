# deps/hold

The one **hold** model of `infra/deps`: `HoldSchema` (`names`, one `version`
or everything from `below` up, a `reason`, an optional upstream `issue`, a
required `reviewBy`), `HOLD_MAX_DAYS` (90 — the longest a hold goes
unreviewed), and the matching and review state (`heldBy`, `holdState`,
`lapsedHolds`, `latestReviewBy`, `holdProblems`, `describeHold`, `utcDay`).

A leaf with nothing but zod behind it, so the deps engine (loaded on every
host, a browser host's worker included) reuses it without pulling in the
Dependency upgrades automation. Its users:

- every updater's holds (`deps/updates`: `heldWaiting`, `reviewableHolds`;
  each updater keeps its own in the file its inputs are declared in) — a host
  daemon's binaries kept behind a release (a Postgres major) included: they
  follow main, so a hold on main is how they stay.

A hold is never released by the calendar: it holds until deleted, and past its
`reviewBy` it is lapsed — work for whoever reviews it.
