# deps/daemon-binaries

The host daemons' binaries (`infra/deps` § Host daemon installs — the
embedded Postgres's `postgres-binaries`, PgBouncer's `pgbouncer-binary`):
what both start scripts call to start on the install main declares, the
report a fallback files, and the health report's **Daemon binaries** row.
Generic: it names no dependency, a new `daemon` declaration shows up with no
change here. Design: `research/2026-11-20-infra-pinned-deps-auto-switch-v2.md`.

Main is the pin: the upgrade that moves the package (`./equin deps upgrade`,
gated by the dependency's `smoke` — a throwaway cluster / socket started on
the new binary) is the one decision, and the daemon runs it from its next
fresh start. Nothing here asks a person to switch.

## Starting (`deps/`)

`startDaemonOnDeclared(dep, { exec, say, start })` — the `deps/` barrel, run
by `database/embedded/scripts/daemon-binaries.ts` and
`database/pgbouncer/scripts/daemon-binary.ts` — wraps the engine's
`startDaemonDep`: says which install the daemon runs, and on a fallback
(`rolled-back`) files the `daemon-binary-rollback` report through the report
outbox (`fileReportFromProcess`). A version already marked failed
(`kept-previous`) is only logged — it was reported when it failed.

## The report (`server/`)

`daemon-binary-rollback` (`ReportKind`, fingerprint per dependency; payload
and `daemonRollbackReport` in `core/`): the daemon runs the previous version,
the failed install is marked so no start retries it, and the task says how to
retry (`./equin deps remove <id>` in main's checkout, then restart the daemon)
or to hold the release on main.

## What the row compares (`machine/internal/check.ts`)

`daemonStatus(dep, { root })` (the engine, read only) for each daemon
dependency, `root` = main's checkout (`getMainRepoRoot` — the gateway runs the
start scripts from there; not a worktree's, not main's served slot): the
install the live daemon was started from (its `<holder>-running` hold), and
what main declares — the same, another (from the next fresh start; `failed`
when a start already fell back from it), or unreadable. Not applicable on a
release (its bundle sealed the binaries) or a checkout with no daemon
dependency.

Pushed (`deps.daemon-binaries`, `needsMachine`), re-read on every advance of
`refs/heads/main` (an upgrade landed) and, while subscribed, any change under
the daemon dependencies' own cache dirs (`deps.daemon-binaries` watcher; `env/`
ignored) — a fresh start moving its running hold, a fallback's
`daemon-failed.json`, a removed install.

## The row (`web/`)

`HealthReport.Row` `daemon-binaries`. `ok` "Up to date with main", or a note
for a version waiting for the next restart ("postgres-binaries 18.6.0 at next
restart"); `attention` when a start fell back ("postgres-binaries 18.6.0
failed to start — running 18.1.0"); `unknown` when main's declaration cannot
be read. Expanded (`DaemonBinariesDetail`): per dependency, what runs against
what main declares, and after a fallback its error and the copyable retry
command.
