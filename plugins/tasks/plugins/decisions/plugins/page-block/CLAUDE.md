# page-block

`<task-decisions task="task-…"/>` — a page block embedding one task's
decisions. Design: `research/2026-11-24-agent-decisions.md` §7.

- **Data is `{ taskId }`, nothing else** (`core/task-decisions-block.ts`):
  the task is known when the block is minted and never changes. `""` is the
  block still asking which task it shows (the slash menu's `/decisions` opens
  a task picker). A deleted task draws "task deleted", never cascades the
  block out of someone's page.
- **In the editor** it draws `TaskDecisionsPanel` (`whenSettled: "show"`),
  answered in place with the inbox's drafts and Submit. The panel is its own
  shortcut region, so two blocks on one page never answer each other's ⌘↵.
- **How it gets onto a page**: an agent writes it with `edit_page` in a region
  it may write (its agent page or an `<agent-inline>` card), typically once
  near the top of its session page; a person inserts it from the slash menu.
  Any task may be named (a supervisor may embed a worker's decisions).
- **A document never mints a dangling one**: the server's
  `Editor.BlockReferenceCheck` refuses a markdown apply creating — or
  re-pointing — a block at a task that does not exist (or at no task); keeping,
  moving or deleting one is never refused. Parse itself only checks the
  attribute is a task id. The bound: only the markdown path is checked — the
  slash-menu picker offers only real tasks, and a raw PATCH is not checked.
- **In `read_page`** the block projects per reader (`Editor.BlockProjection`,
  `server/internal/projection.ts`; the read's `reader` is agent-access's
  conversation):
  - another agent reads the task's decisions BOUNDED, read-only, as the
    tag's derived body (`decisions="4 open, 3 closed"`, `shown="excerpts — …"`):
    the open ones most pressing first (Needs you, Sent, FYI; then the oldest)
    as a `<decision …>` line (id, label, state, where it stands, opened,
    question, from, `thread="N"`), its body cut to one quoted line of
    `BODY_EXCERPT_CHARS` (240), its options (`<option key="A" text="…"
    recommended="true"/>`), then `</decision>` — while they fit in
    `DETAIL_CHARS` (8k); the `RECENT_CLOSED` (5) latest closed as one line
    each (question and outcome cut); every other decision as an index line
    `<decision id="dec-…" label="D7" state="closed"/>`. Every id is on the
    page and `read_decision` (tasks/decisions) returns any one in full —
    body, options, thread. A task at the record's caps projects under 30k
    chars (`projection.test.ts`); the bounds and why are on
    `server/internal/projection.ts`;
  - the agent whose own task it is reads one stub:
    `<task-decisions title="…" own="4 open, 3 closed" task="task-…"/>` — it has
    its tool results, the answer turns and `list_decisions`;
  - `title` is the task's current title; `missing="task deleted"` when the
    task is gone.
  Every attribute but `task`, and the whole body, are discarded on parse, so
  both projections round-trip through `edit_page` unchanged
  (`server/internal/page-tools.test.ts`).
