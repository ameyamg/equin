# find-in-surface

Ctrl+F inside one surface — the browser's find, scoped to a region and
drawn in the app's chrome.

```tsx
<FindScope>                          // common ancestor of the region and its bar
  <PaneChrome overlay={<FindBar label="Find in page" />}>
    <FindRoot>…content…</FindRoot>   // what is searched; adds no box (display: contents)
  </PaneChrome>
</FindScope>
```

The region and the bar sit apart on purpose: the bar belongs in a layer that
does not scroll (beside the scroller), the region inside the scroller. They
meet through a `dom-scope` (`internal/find-root-scope.ts`). The Pages panes
are the first host (`apps/pages/page-tree`'s `PageSurface`).

## What is searched is what is drawn

`internal/region-text.ts` reads the region's text as it reads on screen —
never a data model. So it works on any surface without an adapter, and it
cannot find what the reader cannot see:

- an element with no box contributes nothing; a closed toggle whose body is
  unmounted (the page editor's) is simply not searched;
- a line break sits where the reader sees one — between two boxes that are
  not inline, and at a `<br>` — and a line break in the HTML source is a space
  (unless the element preserves white space, a code block).

A virtualized list (a `DataView` drawing only its visible rows) is the known
gap: rows off screen are not in the DOM. Searching one needs a data-side
source of matches and a way to scroll to a row — not built.

## Matching (`core/`)

`findPattern(query, { matchCase, wholeWord })` — a line break in the query
matches a line break (indentation around it ignored); other spaces match any
run of spaces on one line. `startPoint` / `endPoint` map a match back to text
nodes when it starts or ends on a line break that belongs to no node.

## Painting

Matches are painted with the CSS Custom Highlight API (`find-match`,
`find-match-active`), never by wrapping text in elements — a wrapper would
fight the page editor's Lexical / Yjs reconciliation. The rules are scoped to
`[data-find-root] > *` (an unscoped `::highlight()` costs a style computation
on every element of the document). Colours are the theme's `--find-match`,
`--find-match-active` and `--find-match-active-foreground`
(`ui/tokens/color-palette`). Several bars may paint at once (two panes);
`internal/paint.ts` registers the union.

Ranges are re-read on every DOM change in the region (a `MutationObserver`,
one read per frame): the current match stays the same one, or the next after
it when it went away. Only what the reader did — open, type, step — scrolls.

## Who gets Ctrl+F

`internal/claim.ts`: the region (or its open bar) holding focus, else the
visible region last pressed in, else the only visible region. Otherwise no
bar claims it and the browser's own find opens. Two panes in one tab are one
surface, so the surface gate alone cannot choose.

## Keys

In the field: Enter, or ↓ on its last line — next; ↑ on its first line —
previous; Shift+Enter — a new line; Esc — close. ⌘G / ⇧⌘G step from anywhere
in the region while the bar is open. The bar, query and options are kept view
state (`search.find-bar`): a reload gives them back.
