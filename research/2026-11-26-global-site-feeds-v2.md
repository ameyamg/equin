# Site feeds v2 — items owned by the feed, published to every copy of the site

Follows `research/2026-11-25-global-site-feeds.md` (shipped). Task: task-1795618017-ge65r4.

## Context

The user wants to test tips using only the UI, and wants the local instance's
website (`http://equin.localhost:<port>/about/tips`) to show the same tips as
equin.ai. v1 kept each item under one deployment and published only to that
deployment's box over SSH, so the local instance's own `site_feed_entries` (it
runs the website app, box half included) stayed empty, and nothing could be
tried without a remote box.

## Decisions

### 1. An item belongs to its feed, not to a deployment

- `site_feed_items` loses `deployment_id` (migration generated by the build; v1
  data is test data only). Its `state` (draft | published) is the user's
  intent.
- Per-destination state moves to `site_feed_publications (item_id, destination,
  state publishing|published|unpublishing|failed, error, published_at,
  updated_at)`, `destination` = `local` | `deployment:<id>`.
- Syndication settings become per (feed, target) — no deployment.

### 2. Destinations = every copy of the site that serves the feed

- **`local`** — this instance, always (it runs the website app; the box half's
  server registry knows the feed). Published by calling the box's upsert /
  delete in-process (export them from `site-feeds/box/server`), linking the same
  local attachments to the entry — no transfer.
- **`deployment:<id>`** — every deployment whose composition closure includes the
  feed's declaring plugin (the server-side twin of `useDeploymentShips`; reuse
  what `plugin-meta/composition` resolves), over SSH as in v1.
- **Remote destinations only from the instance that owns deployments.** A
  worktree's DB is a fork holding equin.ai's deployment row; a worktree must
  never publish to production. Reuse whatever rule `remote-deploy` applies to
  deploying from a worktree; if none exists, remote destinations are listed but
  publishing to them is refused off main, said so in the UI.
- Publish / unpublish / an edit of a published item fan out one job per
  (item, destination). Each destination's chip shows its state; Retry per chip.
  A deployment added later shows the item as "not on this site" with Publish.

### 3. Where the editor lives

Feeds no longer hang off one site: a **Feeds** page in the Deploy app's sidebar
lists every feed this instance declares (`useSiteFeedDeclarations()`), each with
its items DataView, item editor, "Also post to" settings, and the destinations
row. The site page's Feeds tab goes (or becomes a link to the page filtered by
nothing — prefer removing it).

### 4. Syndication fires once per item

Syndication (post / edit / remove) runs on the item's intent, once the first
destination succeeds — the first remote deployment if one is enabled, else
local — never once per destination. `SyndicatedPost.url` uses the first
deployment's hostname (local URL when there is none). The Discord message
includes the link.

### 5. "Send test post"

Generic, in `syndication`: in each target's settings, **Send test post** posts the
currently open item through the target's `post` with the config as entered,
records nothing, and shows the target's answer (Discord: the message link). The
user points it at a private channel's webhook.
